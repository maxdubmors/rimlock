# Toolchain and store policies

Research for ticket [#8](https://github.com/maxdubmors/rimlock/issues/8). Researched 2026-10-06. Feeds the decision in #11; this document does not make that choice.

## Question

Is pnpm + WXT + Svelte 5 (with a Rust → WASM KDBX core) a sound toolchain for the Extension, and what do the Chrome Web Store and AMO require?

## Summary

- **WXT is actively maintained but still pre-1.0** (v0.21.4, Aug 2026; monorepo packages released Oct 2026). It builds Chrome MV3 and Firefox MV3 from one codebase, has an official Svelte 5 module and a Vitest plugin with an in-memory fake `browser`. It does **not** automate Safari; it emits a Safari build directory that Apple's packager turns into an app. Most commits come from one maintainer.
- **Rust → WASM works in WXT with no custom plumbing.** A scratch build (WXT 0.21.4, Vite 8.3.2, Svelte 5.57.2, wasm-bindgen 0.2.129 `--target web`) loaded and ran the WASM module in the Chrome 154 **service worker, offscreen document and Svelte popup**. The required step is declaring `'wasm-unsafe-eval'` in the manifest CSP. Without it, all three contexts failed with a CSP `CompileError`, which matches Chrome's documented default.
- **Alternatives are weaker.** Plasmo has had no commit since May 2025. CRXJS is active again but is a Chrome-first Vite plugin with thin Firefox and Safari docs. Extension.js is active but was not evaluated in depth.
- **Chrome Web Store:** bundled WASM is fine. Remote code (JS *or* WASM) is banned. The privacy tab needs a single-purpose statement, a justification for each permission, a remote-code declaration and data-use certification. A privacy policy is required **even if all data stays local**, and passwords count as "authentication information". Review usually takes "a few days" to "a few weeks". Broad host permissions and sensitive permissions are named as things that slow review. There is no published timeline for password managers specifically.
- **AMO:** bundled/transpiled code (WASM included) requires a **source upload plus build instructions that reproduce the output byte-for-byte**. Reviewers default to **Ubuntu 24.04 on ARM64 with Node 24 and npm**, so pnpm and the Rust toolchain must be documented or scripted. All new extensions must declare `data_collection_permissions` (built-in consent; `["none"]` is valid). MV3 is supported, and Mozilla has no plans to deprecate MV2. Firefox has **no background service worker** (MV3 uses event-page `background.scripts`) and **no `offscreen` API**.
- **Safari is not precluded,** but it needs an Apple Developer Program membership and goes through an Xcode/App Store (or App Store Connect web packager) pipeline outside WXT.

## Findings

### 1. WXT: maturity, maintenance, browsers, Svelte, testing

**Maturity and maintenance**
- Repo `wxt-dev/wxt`: ~10.6k stars, MIT, not archived, last push 2026-10-06, 203 open issues ([GitHub API, repos/wxt-dev/wxt](https://github.com/wxt-dev/wxt)).
- Latest core release `wxt-v0.21.4` on 2026-08-11. `wxt-v0.21.3` was on 2026-07-31. Side packages (`storage-v1.3.0`, `i18n-v0.2.8`, `analytics-v0.5.7`) shipped on 2026-10-04 ([releases](https://github.com/wxt-dev/wxt/releases)).
- Still 0.x. The public "Roadmap to v1.0" issue is open, and several pre-1.0 items are unchecked, some marked as potentially breaking ([wxt#920](https://github.com/wxt-dev/wxt/issues/920)).
- Bus factor: `aklinker1` has ~1,268 all-time commits. The next human contributor has 42. Since 2026-04-01, 46 of ~100 commits are his, and the rest come from many one-off contributors ([contributors API](https://github.com/wxt-dev/wxt/graphs/contributors), [commits API](https://github.com/wxt-dev/wxt/commits/main)).
- The proposal to drop MV2 before 1.0 was closed as not planned (2026-02-22) ([wxt#2151](https://github.com/wxt-dev/wxt/issues/2151)).
- WXT 0.21.4 accepts Vite `^6.3.4 || ^7 || ^8`. The scratch build used Vite 8.3.2 ([packages/wxt/package.json](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/package.json)).

**Chrome + Firefox MV3 from one codebase**
- Supported targets are Chrome, Firefox, Safari, Edge and custom browsers via `-b`. **By default WXT builds MV2 for Firefox and Safari** and MV3 for everything else. Override with `--mv3` or `manifestVersion` ([Targeting different browsers](https://wxt.dev/guide/essentials/target-different-browsers.html)). Source: `manifestVersion ?? (browser === 'firefox' || browser === 'safari' ? 2 : 3)` ([resolve-config.ts](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/internal/resolve-config.ts)).
- Verified in the scratch build: one `defineBackground({ type: 'module' })` entry produced `"background": {"service_worker": "background.js", "type": "module"}` for `chrome-mv3` and `"background": {"scripts": ["background.js"], "type": "module"}` for `firefox-mv3`.
- WXT does **not** add `'wasm-unsafe-eval'` to production manifests. Its default MV3 CSP constant is used only by `addDevModeCsp` (dev server) ([manifest.ts](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/internal/manifest.ts)). The project must set `manifest.content_security_policy` itself.

**Safari**
- "WXT does not currently support automated publishing for Safari." You pass `.output/safari-mv2` or `.output/safari-mv3` to Apple's `safari-web-extension-packager` ([Publishing](https://wxt.dev/guide/essentials/publishing.html)).

**Svelte 5 integration**
- Official `@wxt-dev/module-svelte` v2.0.5 has peer deps `wxt >=0.18.6` and `svelte >=5`, and depends on `@sveltejs/vite-plugin-svelte >=4` ([package.json](https://github.com/wxt-dev/wxt/blob/main/packages/module-svelte/package.json)). It worked in the scratch build with Svelte 5.57.2 (released 2026-10-06, [releases](https://github.com/sveltejs/svelte/releases)).
- Svelte supports `<script lang="ts">` for type-only TS without a preprocessor. Props are typed via `$props()`, and `svelte-check` type-checks in CI ([Svelte TypeScript docs](https://svelte.dev/docs/svelte/typescript)).

**Testing**
- `WxtVitest()` plugin for Vitest. It applies the WXT Vite config, auto-imports and aliases, and polyfills `browser` with `@webext-core/fake-browser`, which implements storage in memory ([Unit testing](https://wxt.dev/guide/essentials/unit-testing.html)).
- Svelte recommends Vitest (+ `@testing-library/svelte`) for unit/component tests and Playwright for E2E ([Svelte testing docs](https://svelte.dev/docs/svelte/testing)).
- Playwright extension testing works **only in Chromium**, with a persistent context and the `chromium` channel for headless, "because Google Chrome and Microsoft Edge removed the command-line flags needed for side-loading extensions" ([Playwright: Chrome extensions](https://playwright.dev/docs/chrome-extensions)). Firefox E2E needs a different harness (e.g. `web-ext`). Not evaluated.
- In the scratch test, Chrome for Testing 154 + `puppeteer-core` (`enableExtensions`) loaded the unpacked build headlessly and could read results from the service worker, the offscreen document and the popup.

### 2. Bundling Rust → WASM (wasm-bindgen / wasm-pack) into WXT

**Tool status**
- The `rustwasm` GitHub org was sunset (announced 2025-07-21, archived Sept 2025). wasm-bindgen moved to a new `wasm-bindgen` org with new maintainers ([Inside Rust blog](https://blog.rust-lang.org/inside-rust/2025/07/21/sunsetting-the-rustwasm-github-org)).
- `wasm-bindgen/wasm-bindgen`: active, `0.2.129` released 2026-09-25 ([releases](https://github.com/wasm-bindgen/wasm-bindgen/releases)). `rustwasm/wasm-pack` now resolves to `wasm-bindgen/wasm-pack`, with releases `v0.14.0` (2026-01-20) and `v0.15.0` (2026-05-15) ([releases](https://github.com/wasm-bindgen/wasm-pack/releases)). wasm-pack survived the sunset, but it is optional: `cargo build --target wasm32-unknown-unknown` + `wasm-bindgen` CLI is enough. This matters for AMO's rule that "Build tools or environments that no longer appear to be supported by their maintainers are not accepted" ([AMO policies §3.1](https://extensionworkshop.com/documentation/publish/add-on-policies/)).

**Which output target**
- The wasm-bindgen deployment guide: `--target bundler` assumes WASM-as-ES-module, and "Currently the only known bundler known to be fully compatible with wasm-bindgen is webpack." `--target web` is "directly loadable in a web browser" and needs manual init ([Deploying Rust and WebAssembly](https://wasm-bindgen.github.io/wasm-bindgen/reference/deployment.html)). For Vite/WXT, `--target web` is the low-friction choice.
- WXT's own WASM guide copies the `.wasm` into the output with a module hook and passes `browser.runtime.getURL(...)` to `init`. In content scripts it also needs `web_accessible_resources` ([WXT assets: WASM](https://wxt.dev/guide/essentials/assets.html)).

**Scratch build (performed 2026-10-06, outside the repo)**
- Setup: Rust 1.98.1, `wasm32-unknown-unknown`, `wasm-bindgen-cli 0.2.129`, a trivial `#[wasm_bindgen] fn greet`, `--target web`. Node 26.10, pnpm 11.28.4, WXT 0.21.4, Vite 8.3.2, `@wxt-dev/module-svelte` 2.0.5, Svelte 5.57.2. The glue was imported via an `@/wasm/core` alias from three entrypoints: background, an unlisted `offscreen` page and a Svelte popup.
- Build: **no plugin or copy hook was needed.** Vite recognised wasm-bindgen's `new URL('core_bg.wasm', import.meta.url)`, emitted `assets/core_bg-<hash>.wasm` and rewrote the reference to `new URL('/assets/core_bg-<hash>.wasm', self.location.href)`. That form works in both service-worker and page contexts. The glue landed in a shared chunk with a misleading name (`chunks/_virtual_wxt-plugins-*.js`). This is cosmetic.
- Runtime in Chrome for Testing 154.0.8037.92 (headless, via puppeteer-core):
  - service worker: `hello background from rust` ✔
  - offscreen document (created from the SW with `reasons: ['WORKERS']`): `hello offscreen from rust` ✔
  - Svelte popup: `hello popup from rust` ✔
  - **Negative test**: with the `content_security_policy` removed, all three failed with `CompileError: WebAssembly.instantiateStreaming(): ... neither 'wasm-eval' nor 'unsafe-eval' is an allowed source ... "script-src 'self'"`.
- Firefox: `wxt build -b firefox --mv3` produced a valid MV3 manifest. `addons-linter` (run via `pnpm dlx`) reported **0 errors** and 2 warnings: (a) `offscreen` is an invalid permission in Firefox, which was expected because the test listed it unconditionally; (b) `UNSAFE_VAR_ASSIGNMENT` on `innerHTML` inside the **Svelte runtime** (`template.innerHTML = ...`, used to clone compiler-generated static templates). Runtime in Firefox was **not** tested because no Firefox was available.
- `wxt zip -b firefox` produced a sources zip containing the `.ts/.svelte` files, `pnpm-lock.yaml` and the **prebuilt** `wasm/core_bg.wasm` + glue, but not the Rust sources. The crate lived outside the WXT root. `zip.sourcesRoot` defaults to the WXT root and is configurable ([resolve-config.ts](https://github.com/wxt-dev/wxt/blob/main/packages/wxt/src/internal/resolve-config.ts)), so in a monorepo it must point at the repo root and the zip must include the Rust crate and `Cargo.lock`.
- Reproducibility probe: the same crate built in two different directories gave byte-identical `.wasm` (sha256 `b2368cee…`). This is only a weak signal. The crate had no dependencies or panic paths, and real crates embed `$CARGO_HOME/registry/...` paths in panic messages.

**Context constraints relevant to where the core runs**
- Chrome MV3 supports only `background.service_worker`. Firefox does **not** support `background.service_worker` (bug 1573659) and runs `background.scripts` as event pages. Safari supports both ([MDN: background](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background)).
- `offscreen` is Chrome 109+, MV3 only. Only `runtime` is available inside it, and one offscreen document can be open at a time ([Chrome offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen)). It is not in MDN's WebExtensions compat data, so treat it as Chrome-only ([mdn/browser-compat-data webextensions/api](https://github.com/mdn/browser-compat-data/tree/main/webextensions/api)).
- In Firefox MV3, "content scripts are subject to the same CSP as other parts of the extension", and `'wasm-unsafe-eval'` "must be specified in the CSP if an extension is to use WebAssembly" ([Firefox MV3 migration guide](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/)).
- Chrome now supports the standard `browser.*` namespace from Chrome 148 (banner on [Chrome offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen)). Safari supports both `chrome.*` and `browser.*` ([Apple: browser compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)).

### 4. Chrome Web Store policies

- **WASM / CSP**: the default MV3 `extension_pages` CSP is `script-src 'self'; object-src 'self';`, and with it "WebAssembly will be disabled". The minimum policy Chrome allows is `script-src 'self' 'wasm-unsafe-eval'; object-src 'self';`, and it "cannot be relaxed beyond this minimum" (e.g. no `'unsafe-eval'`, which is an install-time error) ([Chrome: manifest CSP](https://developer.chrome.com/docs/extensions/reference/manifest/content-security-policy)). The scratch test confirmed this.
- **Remote code ban**: remotely hosted code is "anything that is executed by the browser that is loaded from someplace other than the extension's own files. Things like JavaScript and WASM", and it excludes data like JSON or CSS ([Chrome: remote hosted code](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)). MV3 policy: "the full functionality of an extension must be easily discernible from its submitted code". Banned: external `<script>`, `eval` of fetched strings, and interpreters for remote commands. Allowed: syncing user data with a server, and "server-side operations with data (such as for the purposes of encryption with a private key)" ([MV3 requirements](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements)).
- **Code readability**: no obfuscation. Minification (whitespace removal, renaming, collapsing files) is allowed ([Code readability](https://developer.chrome.com/docs/webstore/program-policies/code-readability)). The review docs suggest "submitting your code as authored" where possible ([Review process](https://developer.chrome.com/docs/webstore/review-process)).
- **Permissions**: "Request access to the narrowest permissions necessary ... Don't attempt to 'future proof'" ([Use of permissions](https://developer.chrome.com/docs/webstore/program-policies/permissions)). The dashboard Privacy tab requires a **single purpose description**, a **justification per permission**, a **remote code declaration** ("Extensions that call remote code and do not declare and justify it ... will be rejected"), **data usage certification** and a **privacy policy link** ([Fill out the privacy fields](https://developer.chrome.com/docs/webstore/cws-dashboard-privacy)).
- **User data**: passwords and logins are "Authentication information". Disclosure is required "even when data is processed or stored locally on a user's device". A privacy policy is required even for local-only storage. Data must be handled securely, and authentication information must never be publicly disclosed ([User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq), [Privacy policies](https://developer.chrome.com/docs/webstore/program-policies/privacy), [Limited use](https://developer.chrome.com/docs/webstore/program-policies/limited-use)).
- **Review times**: "For most extensions, review is completed within a few days, but it can take up to a few weeks". Contact support after 3 weeks. Signals that trigger closer review: new developers, new extensions, dangerous permission requests, significant code changes. Broad host permissions (`<all_urls>`, `*://*/*`), sensitive execution permissions, large or hard-to-review code, and minification all lengthen review ([Review process](https://developer.chrome.com/docs/webstore/review-process)). **No password-manager-specific timeline is published.** A new developer's new extension with autofill-style host access hits several of these signals at once.
- **MV2 is gone**: MV2 was disabled everywhere with Chrome 138 (2025-07-24), and all remaining MV2 items were removed from the store on 2026-08-31 ([MV2 timeline](https://developer.chrome.com/docs/extensions/develop/migrate/mv2-deprecation-timeline)).

### 5. AMO (addons.mozilla.org) policies

- **Source code submission**: "Add-ons may contain transpiled, minified or otherwise machine-generated code, but Mozilla needs to review a copy of the source code before any of these steps have been applied", together with build instructions. Dependencies must be included or fetched "only through the respective official package managers". "Build tools or environments that no longer appear to be supported by their maintainers are not accepted." There must be no obfuscation, and no remote code may be loaded for execution ([Add-on policies §3.1, §4](https://extensionworkshop.com/documentation/publish/add-on-policies/)).
- **Reproducibility**: reviewers rebuild and diff, and "There must be no differences". Sources must cover bundler or "any other custom tool" output, and must be attached to **every version**. The limit is 200 MB. Tools must be open source and runnable locally. Include lockfiles ([Source code submission](https://extensionworkshop.com/documentation/publish/source-code-submission/)). The guide explicitly allows tools that "transpile code from other languages", so a Rust → WASM build is in scope and must be reproducible from the Rust source.
- **Default reviewer build environment**: "Ubuntu 24.04.4 LTS (Desktop edition), ARM64 CPU architecture, 10GB RAM, 6 vCPU, Node 24.14.0 and npm 11.9.0". "You must let the reviewers know if any of the above differs from your build environment" ([Source code submission](https://extensionworkshop.com/documentation/publish/source-code-submission/)). So pnpm and the Rust toolchain (rustup, pinned version, `wasm32-unknown-unknown`, `wasm-bindgen-cli`) must be in the README or a build script. **The reviewer's host is ARM64, so the WASM must be byte-identical when built on aarch64**, which nobody has verified yet.
- **Third-party libraries**: npm `package.json` counts as the library link. Only release versions are allowed, and modifications are not ([Third party library usage](https://extensionworkshop.com/documentation/publish/third-party-library-usage/)). Crates.io dependencies are not mentioned there. Presumably `Cargo.lock` serves the same purpose, but that is unverified.
- **WASM CSP**: Firefox MV3 permits only `'none'`, `'self'` and `'wasm-unsafe-eval'` in script directives ([MDN: content_security_policy](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/content_security_policy)). `addons-linter` accepts `'wasm-unsafe-eval'` (`CSP_KEYWORD_RE`, [addons-linter const.js](https://github.com/mozilla/addons-linter/blob/master/src/const.js)), and the scratch build linted clean on CSP.
- **Data collection disclosure**: from 2025-11-03 all **new** extensions must use Firefox's built-in data collection consent via `browser_specific_settings.gecko.data_collection_permissions`. `"required": ["none"]` declares no collection. Passwords fall under `authenticationInfo`, which is never eligible for implicit consent. The built-in consent works in Firefox desktop 140+ and Android 142+, and older versions still need a custom consent experience ([Firefox built-in data consent](https://extensionworkshop.com/documentation/develop/firefox-builtin-data-consent/), [policies §6.2](https://extensionworkshop.com/documentation/publish/add-on-policies/)). "Data transmission" is data "handled outside of the add-on or the local browser" (§6), so purely local vault handling is not transmission.
- **MV3 status**: Firefox supports MV3 with event-page backgrounds (non-persistent since Firefox 106). MV3 removes persistent background pages ([Firefox MV3 migration guide](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/)). Mozilla says it has no plans to deprecate MV2 and promises ≥12 months' notice if that changes ([Mozilla add-ons blog, Mar 2024](https://blog.mozilla.org/addons/2024/03/13/manifest-v3-manifest-v2-march-2024-update/)).
- **Review timing**: all add-ons get automated validation, and "It can take up to 24 hours ... to be signed and published, or longer if your submission is selected for manual review". Manual code review can happen "at any time after submission" ([Signing and distribution overview](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/)).
- **WXT support**: `wxt zip -b firefox` builds both the extension zip and a sources zip, excludes tests, config and hidden files, and recommends a README / `SOURCE_CODE_REVIEW.md` with build steps. It warns that `.env` files affect output hashes ([WXT Publishing](https://wxt.dev/guide/essentials/publishing.html)).

### 6. Safari (must not be precluded)

- Apple's `xcrun safari-web-extension-packager` (formerly `-converter`) wraps an existing web extension into an Xcode project with a macOS/iOS host app ([Packaging a web extension for Safari](https://developer.apple.com/documentation/safariservices/packaging-a-web-extension-for-safari)). A **web-based packager in App Store Connect** needs "no Mac or access to Xcode". It does require Apple Developer Program enrollment, and packaging time counts against Xcode Cloud's 25 h/month ([Packaging and distributing with App Store Connect](https://developer.apple.com/documentation/safariservices/packaging-and-distributing-safari-web-extensions-with-app-store-connect)).
- Safari 15.4+ supports MV2 and MV3. `storage.session` needs Safari 16.4+, and `storage.sync` does not sync. The local storage limit is 5 MB unless `unlimitedStorage` is set (Safari 16+). On iOS, background must be non-persistent ([Apple: browser compatibility](https://developer.apple.com/documentation/safariservices/assessing-your-safari-web-extension-s-browser-compatibility)).
- Safari accepts `background.scripts` and `background.service_worker`. It prefers scripts unless `preferred_environment: ["service_worker"]` is set ([MDN: background](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background)).
- Implication: a design that keeps the KDBX core runnable in **both** a service worker (Chrome) and an event page (Firefox, Safari default) and does not *require* `offscreen` keeps Safari open.

## Toolchain assessment

| Component | Assessment | Confidence |
|---|---|---|
| **pnpm** | Works with WXT (v11.28.4 in scratch). pnpm 11 enforces supply-chain checks such as `minimumReleaseAge`, which flagged a same-day Svelte release. AMO reviewers default to npm, so pnpm version and install must go in the build README (e.g. via Corepack). | High |
| **WXT** | Fits the Chrome + Firefox MV3 requirement, has Svelte and Vitest stories, and produces AMO source zips. Risks: pre-1.0 API churn, single main maintainer, non-obvious defaults (Firefox/Safari default to MV2; production CSP is not set for WASM). Both defaults are fixable in config. | Medium-high |
| **Svelte 5** | Official WXT module, type-only TS in components, `svelte-check` for CI. The only store friction found is a linter *warning* on `innerHTML` inside the runtime. | Medium-high |
| **Rust → WASM (wasm-bindgen `--target web`)** | Verified end-to-end in Chrome SW, offscreen and popup with zero custom bundler config. wasm-bindgen is actively maintained under its new org. Main costs: AMO reproducible build of the Rust part on ARM64, plus a toolchain the reviewer must install. | High for Chrome; Medium for AMO acceptance |
| **Plasmo** | Not recommended (stalled since May 2025). | High |
| **CRXJS / plain Vite** | Viable fallbacks with more manual cross-browser work. | Medium |

For #11: the hypothesis stack works, with three conditions. (1) Pin MV3 for Firefox explicitly and set the `'wasm-unsafe-eval'` CSP. (2) Make the KDBX core context-agnostic (SW / event page / page), since `offscreen` is Chrome-only. (3) Budget for a scripted, pinned, reproducible Rust build that an AMO reviewer can run on ARM64 Ubuntu.

## Open risks / unknowns

1. **AMO reproducibility of the WASM on ARM64.** Nobody has verified that an x86_64 build and an aarch64 build of a real crate (keepass-rs plus crypto deps) produce identical `.wasm`. Absolute paths in panic strings (`$CARGO_HOME`, the project path) will differ between machines unless remapped (e.g. `--remap-path-prefix`) or built in a pinned container. `wasm-opt`, if used, adds another version-pinned tool. Worth a ticket.
2. **Will AMO reviewers install a Rust toolchain?** Policy allows transpiling from other languages and asks you to state deviations from their environment, but no AMO doc mentions Rust or WASM specifically. A dry-run submission (unlisted) would de-risk this.
3. **Firefox runtime was not tested** in the scratch build. Only the build and `addons-linter` were. WASM in a Firefox MV3 event page and in extension pages still needs a smoke test.
4. **Safari runtime was not tested.** CSP `'wasm-unsafe-eval'` behaviour in Safari extensions is not documented on the Apple pages reviewed.
5. **CWS review time for a password manager** is unpublished. Expect extra scrutiny: new developer, new item, authentication data, likely `<all_urls>`-style host access or `scripting`/`activeTab` for autofill. Permission strategy (e.g. `activeTab` + optional host permissions) affects review time and is a design question in its own right.
6. **WXT 1.0 breaking changes.** The v1.0 roadmap still has open "potentially breaking" items. Pin exact versions and expect migration work.
7. **Svelte `innerHTML` linter warning** on AMO. It is a warning, not an error, but a reviewer may ask about it. Unknown whether that has caused rejections for other Svelte extensions.
