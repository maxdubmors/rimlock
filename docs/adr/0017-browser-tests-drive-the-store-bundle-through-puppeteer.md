# Browser tests drive the store bundle through Puppeteer

End-to-end tests load the Extension into Chrome for Testing and Firefox, both pinned and headless, and drive them with Puppeteer (CDP for Chrome, WebDriver BiDi for Firefox), with Vitest as the runner. They load the same release bundle that goes to the stores. That bundle has no test hooks, no test build flavour and no flag-gated debug entrypoints: time is moved by fake clocks that Puppeteer installs in page contexts and by the shortest values the Settings schema allows, and anything that cannot be reached that way is tested one level down, where clocks are injected. The autofill fixtures are tested one level down too: the label `FormDetector` gives a field never leaves the content script's isolated world, so they run `FormDetector` in a test extension of their own, a manifest and a content script, in the same pinned browsers. The store bundle's form detection is tested through the Inline menu and Fill, in an end-to-end scenario on a few of the same fixtures. Below the browser, the background is tested against `FakeCore` and `FakeSource`. A fake is allowed only together with a contract suite that runs the same tests against the fake and against the real implementation (the WASM Core; the WebDAV adapter against a Docker server matrix; the Chrome local-file adapter on OPFS handles), so a fake that drifts from reality fails a test instead of hiding a bug. Snapshots of third-party sites never enter the repository: the autofill suite in the repository is synthetic, and the live corpus is a list of URLs with expected labels, run by hand on every Proton bump, with each miss reduced to a synthetic fixture.

## Considered Options

- **Playwright.** Rejected: it loads extensions only in Chromium; its Firefox is a patched build that cannot run an MV3 Extension, so Firefox would need a second tool. Puppeteer already ran a real MV3 content script in both browsers in [Compare form-detection engines: Proton classifier vs Bitwarden heuristics](https://github.com/maxdubmors/rimlock/issues/17) and [Verify Proton classification across shadow roots](https://github.com/maxdubmors/rimlock/issues/24).
- **WebdriverIO with chromedriver and geckodriver.** Rejected: both browsers work, but it brings a heavier, separate ecosystem for no capability Puppeteer lacks here.
- **A test build flavour with hooks** (fake clock, state injection behind `import.meta.env.TEST`). Rejected: the tested bundle would differ from the shipped one, and build-only failures (CSP, WASM loading, minification) would escape. Hooks in the shipped build are attack surface.
- **Autofill fixtures on the store bundle, observed through the Inline menu or Fill.** Rejected: behaviour does not tell every label apart (a username field and a current-password field open the same Inline menu), the fill-time checks hide a classifier miss on a hidden field, and each fixture would need an Unlocked Database with a Matching Entry. The test extension is not a test build flavour: it holds `autofill/`'s `FormDetector` and nothing else of the Extension, and the store bundle stays as shipped. Decision detail: [Observe FormDetector's labels through the store bundle](https://github.com/maxdubmors/rimlock/issues/137).
- **Real WASM in every TypeScript test.** Rejected: TypeScript-only work would need a Rust toolchain, and the fast tier would slow down.
- **Committing the 62 MB of live-page snapshots, or keeping them in Git LFS.** Rejected: it redistributes other sites' copyrighted pages in a GPL repository.

## Consequences

- Where Firefox's BiDi support is narrower than CDP, a scenario that cannot be expressed goes to the manual pre-release checklist; it does not bring in a second tool.
- Picker-based flows cannot be automated (`showOpenFilePicker` is not interceptable), so adding a Database in end-to-end tests goes through WebDAV in Chrome and import `<input type=file>` in Firefox; the File System Access permission lifecycle stays on the manual checklist. Until M1's add flow exists, the M0 walking skeleton adds a Database through `<input type=file>` in both browsers ([`plan.md`](../spec/plan.md) § M0).
- The wake-up rebuild criterion of ADR-0005 is measured in the same harness on the store bundle.
- The test extension is built apart from the store bundle, so the autofill fixtures do not test the store bundle's build of the `content` entrypoint; the end-to-end scenario on the fixtures does ([`engineering.md`](../spec/engineering.md) § Tests).
- Decision detail: [Decide the testing strategy](https://github.com/maxdubmors/rimlock/issues/33).
