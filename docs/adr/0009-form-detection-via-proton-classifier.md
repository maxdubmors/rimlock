# Form detection uses Proton's classifier, unmodified, behind a rimlock-owned FormDetector seam

The Extension classifies page fields (username, current password, new password, sign-up identifier, OTP) with Proton's `@protontech/autofill` package, used as an unmodified npm dependency. A rimlock-owned `FormDetector` interface wraps it, so nothing else in the Extension depends on Proton's types. Proton cannot see shadow DOM, so rimlock walks shadow roots itself, closed ones included (`openOrClosedShadowRoot` in the content script), and feeds each root to the classifier. That alone is enough only when a whole form sits in one root. Design-system field components put each `<input>` in its own root (Reddit), and there Proton loses the form: it either never types the field or types the form `noop`. So rimlock adds two steps of its own, using only the package's public exports. A field alone in its root gets Proton's cluster flag (`flagCluster`), so Proton types it. Fields that are alone in their form are grouped with nearby fields across root boundaries, and rimlock sets the group's purpose from the field types in it: a new password makes it a sign-up, a current password a login. On 55 live pages Proton tied with Bitwarden's heuristics (46 vs 45 fully correct), but it was better at form purpose: sign-up vs login, new-password and OTP. The Inline menu, the generator and TOTP fill all depend on purpose, and the package costs no extraction work. Remote per-site rules and model downloads stay off, because the Extension fetches nothing at runtime (ADR-0002).

## Considered Options

- **Fork Bitwarden's heuristics.** Rejected: it is smaller, faster and readable, and it already pierces shadow DOM. But it is weak on form purpose (0/7 OTP fixtures, a missed new-password), and it means owning a ~7k-line fork with a wide `@bitwarden/common` type closure.
- **Write rimlock's own heuristics.** Rejected: no labelled data to tune them on, and the two existing engines already took years of fixes.
- **Vendor a patched Proton copy.** Deferred: AMO accepts third-party code only as unmodified releases, so a patch makes the copy rimlock's own code to review and maintain. Making the package see through shadow roots is not a small patch either: a deep query in Fathom's `dom()` and about 70 DOM call sites, to re-apply on every release. The walk with grouping reached the light-DOM scores without it, so the patch stays only a fallback.

## Consequences

- The model is opaque and has no public repository or training data. rimlock cannot retrain it, only pin a version, wrap its output and override it in rimlock code.
- Proton classifies; it does not decide. rimlock owns the mapping from labels to actions, the fill-time visibility, honeypot and gesture checks, and per-site overrides.
- The walk and grouping use exported but undocumented internals (`flagCluster`, `selectFormCandidates`, `isProcessableField`, …). rimlock also re-implements `shouldRunClassifier()` per root, because the package's version reads only `document`. Pin the version exactly, and run the shadow-DOM fixtures as a regression suite on every bump.
- `chrome.dom.openOrClosedShadowRoot` throws on any element that is not an `HTMLElement` (every `<svg>`), so the walk filters first.
- A split form whose only visible field is an identifier (Reddit's sign-up step 1) gets no purpose and no label. Verified on 16 shadow fixtures, Reddit and archive.org in Chrome and Firefox, with no losses on the live corpus and a walk under 5 ms: [Verify Proton classification across shadow roots](https://github.com/maxdubmors/rimlock/issues/24).
